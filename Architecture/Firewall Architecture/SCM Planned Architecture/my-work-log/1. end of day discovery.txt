30,000-Foot Goal
This project appears to be building a migration-era automation architecture where Cortex XSOAR becomes the orchestration brain for store/firewall lifecycle workflows, while Strata Cloud Manager remains the system of record for firewall management. The intent is to automate business outcomes (store build, replacement, incident response, onboarding) instead of scripting low-level firewall tasks one-by-one.

This direction is documented most clearly in:

XSOAR Q and A/getting-started.md
Meetings/2026-07-09_XSOAR_Discovery.md
How I Read the Target Architecture

XSOAR orchestrates multi-step workflows, state, approvals, and potential rollback.
SCM handles firewall policy/config lifecycle.
Existing PSU, Python, and Ansible assets are reused as execution components.
SolarWinds and similar monitoring systems trigger event-driven automations.
Meraki is a key bootstrap dependency for temporary connectivity during deployment/replacement flows.
What I’d Call Out

Biggest strategic bet: “orchestrate with XSOAR, configure with SCM” is the core architectural decision.
Reuse over rebuild: there is explicit interest in leveraging mature Foot Locker/Palo Alto playbooks rather than creating net-new custom automation everywhere.
Business-intent abstraction: workflows are being framed as outcomes (for example, “enable temporary store connectivity”) instead of device-level operations.
Migration dependency risk: XSOAR licensing access and on-prem-to-cloud timing could materially delay or shape implementation.
API uncertainty risk: licensing operations may still require manual portal steps; full automation feasibility is not yet proven.
Ownership boundaries are not finalized: who owns Meraki DHCP/bootstrap logic (XSOAR vs PSU) is still open.
Documentation maturity gap: most architecture/ADR/API/workflow docs are placeholders today, so the program is in discovery-direction stage, not detailed design completion.
Critical Unknowns to Resolve Early

License and role access for engineering in XSOAR.
Foot Locker XSOAR environment availability and migration timeline.
Existing playbook inventory and extensibility.
SCM snippet variable strategy replacing Panorama-era variable patterns.
Explicit control-plane split: what must live in SCM, XSOAR, PSU, or external systems.
Bottom Line
The project goal is not just “move from Panorama to SCM.” It is to establish a durable automation operating model for merged enterprise operations, with XSOAR as orchestration, SCM as configuration authority, and existing tooling integrated into a hybrid, event-driven workflow platform.
