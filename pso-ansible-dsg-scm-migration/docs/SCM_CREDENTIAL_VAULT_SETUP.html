1 Overview & How It Works

All SCM playbooks in this project use a shared role (roles/scm_auth) that calls the Palo Alto identity provider to obtain a short-lived OAuth2 bearer token. This role reads three credential variables at runtime. Those variables must live somewhere Ansible can find them — and that place must be encrypted, because the values are equivalent to passwords.

Ansible Vault encrypts a YAML file in-place using AES-256-CBC. When Ansible runs, it transparently decrypts the file in memory and injects the variables — no plaintext ever touches disk at runtime.

Where each file lives in the project

project structure — relevant files only
pso-ansible-dicksportinggoods-1445726/
├── .vault_pass                        # plain-text vault password — stays on disk, never in Git
├── group_vars/
│   └── all/
│       └── scm_credentials.yml        # AES-256 encrypted — safe to commit to Git
└── roles/
    └── scm_auth/
        └── tasks/main.yml             # reads the three variables at playbook runtime
Why group_vars/all/? Ansible automatically loads every file under group_vars/all/ for every host and play. Placing the credentials file there means any playbook that calls the scm_auth role will have the variables available without any extra vars_files configuration.

2 SCM Credentials You Need

The scm_auth role posts to the Palo Alto identity provider using the OAuth2 client_credentials grant. Three values are required:

VariableDescriptionWhere to find it
scm_client_id OAuth2 client identifier for your SCM service account Strata Cloud Manager → Settings → Identity & Access → Service Accounts
scm_client_secret OAuth2 client secret — treat this like a password Same service account page — generated when the account is created
scm_tsg_id Tenant Service Group ID — scopes the token to your tenant Strata Cloud Manager → Settings → Tenant (numeric ID in the URL or tenant info page)
Save the client secret immediately SCM only displays the client_secret once at creation time. If you lose it, you must regenerate it, which invalidates all existing automation using the old value.

How the role uses them

For reference, this is the exact POST the scm_auth role makes using these three variables:

roles/scm_auth/tasks/main.yml — auth call (read-only reference)
url:           https://auth.apps.paloaltonetworks.com/oauth2/access_token
method:        POST
body:
  client_id:     {{ scm_client_id }}
  client_secret: {{ scm_client_secret }}
  grant_type:    client_credentials
  scope:         tsg_id:{{ scm_tsg_id }}
# The role registers the returned access_token as scm_access_token,
# which all SCM playbooks then use in their x-auth-jwt header.

3 Create the Vault Password File

The vault password file contains the single passphrase used to encrypt and decrypt scm_credentials.yml. It never changes the encrypted file — it is only the key to unlock it.

  1. Write the passphrase into .vault_pass at the project root. Use printf (not echo) to avoid writing a trailing newline, which can cause decryption failures.

    bash
    # Replace the value below with a strong, unique passphrase
printf 'YourStrongPassphraseHere' > .vault_pass

  2. Restrict file permissions so only the current user can read it.

    bash
    chmod 600 .vault_pass

  3. Make sure .vault_pass is excluded from Git. Check your .gitignore:

    bash
    # Add .vault_pass to .gitignore if not already present
grep -qxF '.vault_pass' .gitignore || echo '.vault_pass' >> .gitignore
Never commit .vault_pass to version control The encrypted scm_credentials.yml is safe to commit. The .vault_pass file is not — committing it would expose every credential it protects. Store it separately: a secrets manager, a protected network share, or hand it to the operator securely out-of-band.

4 Create the SCM Credentials File

Create the credentials file at exactly this path — Ansible loads it automatically because it is under group_vars/all/:

bash — create the directory if it does not exist
mkdir -p group_vars/all

Create group_vars/all/scm_credentials.yml with your actual values. This is the plaintext form before encryption:

group_vars/all/scm_credentials.yml — fill in your values
---
scm_client_id:     "your-client-id-from-palo-alto-hub"
scm_client_secret: "your-client-secret-value"
scm_tsg_id:        "1234567890"
Keep the plaintext file open in an editor — do not close it yet You will encrypt it in the next step. Once encrypted, you cannot read the values directly from the file; you must use ansible-vault view or ansible-vault edit.

5 Encrypt with Ansible Vault

Run the following command from the project root. It encrypts the file in-place — the original YAML content is replaced with an AES-256 ciphertext block.

bash
ansible-vault encrypt group_vars/all/scm_credentials.yml \
  --vault-password-file .vault_pass

After this command completes successfully, the file on disk will look similar to this — the exact hex content will differ each time due to a random IV:

$ANSIBLE_VAULT;1.1;AES256 ← vault format header: version 1.1, AES-256
30333263613535363934623639393032... ← ciphertext, hex-encoded, 80 chars per line
3330643162356230616461353265663...
61633862313730343635343037333836...
... ← no plaintext is recoverable without the vault password
This file is now safe to commit to Git The ciphertext is meaningless without .vault_pass. Committing it to your repository means team members only need the vault password (shared out-of-band) to use it — not access to the SCM portal.

6 Verify the Encryption

Two checks to confirm everything is wired up correctly:

Check 1 — confirm the file header

bash
head -1 group_vars/all/scm_credentials.yml

Expected output:

expected
$ANSIBLE_VAULT;1.1;AES256

Check 2 — decrypt and view the contents

bash
ansible-vault view group_vars/all/scm_credentials.yml \
  --vault-password-file .vault_pass

Expected output — your three variables in plaintext, printed to the terminal, but never written to disk:

expected
---
scm_client_id:     "your-client-id-from-palo-alto-hub"
scm_client_secret: "your-client-secret-value"
scm_tsg_id:        "1234567890"
If you see a decryption error The most common cause is a trailing newline in .vault_pass. Recreate it with printf (not echo) as shown in step 3, then retry.

7 Day-2 Operations

All vault operations are performed with the ansible-vault command from the project root. Always include --vault-password-file .vault_pass.

V
View (read-only, no changes)
bash
ansible-vault view \
  group_vars/all/scm_credentials.yml \
  --vault-password-file .vault_pass
Decrypts to stdout only — file on disk remains encrypted.
E
Edit (open in $EDITOR)
bash
ansible-vault edit \
  group_vars/all/scm_credentials.yml \
  --vault-password-file .vault_pass
Opens the decrypted content in your $EDITOR (nano, vim, etc.). Saves re-encrypted on exit.
K
Re-key (change the vault password)
bash
# Write the new password to a temp file
printf 'NewStrongPassphrase' > .vault_pass_new
chmod 600 .vault_pass_new

ansible-vault rekey \
  group_vars/all/scm_credentials.yml \
  --vault-password-file .vault_pass \
  --new-vault-password-file .vault_pass_new

# Replace the old password file with the new one
mv .vault_pass_new .vault_pass
Use when rotating the vault password. The SCM credential values are unchanged — only the encryption key changes.
D
Decrypt (remove encryption)
bash
ansible-vault decrypt \
  group_vars/all/scm_credentials.yml \
  --vault-password-file .vault_pass
Writes plaintext back to disk. Only use temporarily for inspection — re-encrypt immediately after.

Rotating the SCM client secret

When the SCM service account secret is regenerated in the Palo Alto portal, update the vault file with:

bash — update client_secret after SCM rotation
# Open the file in your editor — change scm_client_secret to the new value, then save
ansible-vault edit group_vars/all/scm_credentials.yml \
  --vault-password-file .vault_pass

No other files need to change — the scm_auth role reads the variable by name at runtime.

8 Using the Vault When Running Playbooks

Every playbook that includes the scm_auth role needs Ansible to unlock the vault at runtime. Pass the vault password file with the --vault-password-file flag:

bash — flag syntax
ansible-playbook playbooks/<any-scm-playbook>.yml \
  --vault-password-file .vault_pass
Set it once in ansible.cfg to avoid typing it every time Add the following line to [defaults] in ansible.cfg. Ansible will automatically use this file for every run in the project directory.
ansible.cfg — add vault_password_file
[defaults]
roles_path          = roles
inventory           = inventory.ini
vault_password_file = .vault_pass

With this setting in place, the flag can be omitted from every command — Ansible resolves the vault automatically:

bash — no flag needed when vault_password_file is set in ansible.cfg
ansible-playbook playbooks/check_bootstrap_status.yml
ansible.cfg must also be excluded from Git if vault_password_file points to a local path If your ansible.cfg is committed to the repository (which is common), the .vault_pass path it references must not exist in the repo — only on each operator's local machine or jump host. The .gitignore entry for .vault_pass covers this.
